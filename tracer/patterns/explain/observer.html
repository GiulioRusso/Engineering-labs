Problem. Several parts of a program must react when something changes: a phone app, a thermostat and a logger all care about the temperature. If the weather station called each of them by name, it would have to change every time a new display was added, and it would depend on all of their classes.

Solution. The station (the subject) keeps a list of objects that implement one small interface, Observer, with a single method update(). Anyone interested subscribes; when the temperature changes the station loops over the list and calls update() on each. It never learns what they are.

  1. Define the interface the subject will call (update).
  2. The subject keeps a list of pointers to that interface, with subscribe and unsubscribe.
  3. On every change, notify() calls update on everyone in the list.
  4. Each observer decides on its own what to do with the news.

Where you meet it

GUI event listeners (a button notifies its click handlers), spreadsheet cells recomputing when a cell they use changes, model–view separation in MVC, publish/subscribe message buses, reactive libraries (signals, RxJS).

Common mistakes

Forgetting to unsubscribe an object that is about to be destroyed: the subject keeps a dangling pointer (in C++ a crash, in garbage-collected languages a memory leak). And relying on the order observers are called in: the pattern promises none.

This scenario: the phone unsubscribes halfway. The second change reaches only the thermostat: the phone still exists, it simply is no longer on the list.
